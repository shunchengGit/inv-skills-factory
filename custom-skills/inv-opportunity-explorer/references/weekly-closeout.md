# 周研检查点与收尾清单

适用于周研、有界委派及超时恢复。复用现有run、报告、计算文件、records和ledger，不新增数据库/事实认证器；机构覆盖与QARP门禁不因时间预算放宽。

## 开工与阶段检查点
- [ ] 研究前建立或续读当日run；记录开始/更新时间、执行方式、实际时限来源、研究截止点、收尾预算、负责验收的代理。时限未知先确认或按保守有界片段执行，不假定cron只有600秒。
- [ ] 每家公司开始即在run建立检查点：company_id、当前步骤、证据/计算/报告/记录路径（未产生为null）、ledger登记与回读状态、research_gate、具体缺口、next_step。started是run/检查点状态，不是ledger阶段；不为占位伪造研究记录。
- [ ] 每完成一组证据核验、一次计算、一个报告段落即保存成果并更新检查点；原始证据与推断分开。不得等全篇完成才首次落盘，也不得将待执行计算写成已执行。
- [ ] 按剩余时间动态收缩范围：600秒子代理示例为0–420秒研究（含预检），420秒后停止扩展来源/启动第二家，至少留120秒处理已有计算、报告、record和run核验，剩余60秒作缓冲。每次耗时调用后重估；收尾预算不足立即partial落盘，不再开新检索。其他时限按实际预算调整，短到无法收尾就不开始整家公司。
- [ ] 先完成一家再决定第二家；第二家只有研究及收尾预算均足够才启动。未启动的候选记“未研究/递延及原因”，不伪造partial台账或计为完成。

## 每家公司立即收尾
1. 保存已有计算输入/输出、报告段落、门禁判定、来源和缺口；研究不足用partial，reason明确缺什么、影响何种结论、下一步补什么。仅调用失败的泛称不够。
2. 保存独立record JSON（保留discovery/coverage契约），再次执行check；核实是本轮结果且允许登记后立即执行`ledger.py record --file <绝对路径JSON>`。不要为等第二家公司而搁置。
3. 读record返回并执行`ledger.py status`回读，核公司、日期、阶段、report_path等；确认无误后才将run中该公司ledger检查点标为已核验。非零退出或不一致必须记缺口，不能计成功。
4. 幂等返回inserted=false不是本次payload已更新：同公司/同日期/同阶段旧记录不会覆盖。回读检查已有内容；不一致时在报告/run保存补证与冲突说明，不直接改库、不改日期规避幂等、不把未写入的新证据说成已登记。

## 超时恢复：只补缺步
- [ ] 接手前确认原worker已结束/取消或明确移交写入权，避免与仍活跃的收尾代理并行改同一run/报告/台账。
- [ ] 先回读报告 → 计算输入/输出 → records与ledger status → run检查点，列出“已有且验收通过/缺失/不一致”。不能仅凭子代理摘要、文件存在或超时标签判断整轮成功/失败。
- [ ] 报告和计算已有且有效、仅漏登记：复核证据门禁、记录字段与check后补record；登记已有、仅run未结束：回读核验后补状态。只对缺失或无效计算/证据执行补做，不重跑已核实来源；时效变化需要刷新时明确原因。
- [ ] 恢复不得把原started直接改成成功。在run记中断原因、恢复时间、完成步骤及遗留缺口；有研究缺口仍partial，即使technical_status=completed。不可用deep_done或“可以买”包装缺证结果。

## 最后回读与交付
- [ ] 报告非空且逐公司结论、实际完成数/未研究数/失败数一致；已声明的本地来源路径存在、计算输出可读。文件校验只是技术检查，原文真实性、机构独立性及估值合理性仍须代理核验。
- [ ] 每个实际研究公司均有可追溯记录与成功登记/回读；阻塞者如实写失败，不凭报告存在算闭环。
- [ ] 写run终态completed/partial/failed、结束时间、technical_status与逐公司research_gate/缺口，然后再次读取run，确认不再started且与报告、ledger一致。写失败就明确交付阻塞，不能宣称成功。
- [ ] 按原模式交付一次摘要；cron自动投递，不重复手动发送。后台长任务用`terminal(background=true, notify_on_complete=true)`保存session_id/日志路径，收到完成通知后由负责代理读退出码及产物并执行本清单；既有cron由执行代理收尾。无人接回验收则不启动。delegate只负责可在预算内闭环的片段，禁止连续10分钟整体重试。调度/通知成功不等于研究通过；本流程不授权新增cron或修改模型/provider。
